# Bug sweep, 2026-11-13

Whole project: ruff over every package, `py_compile` on all 384 files, the test suite, all 24 live API endpoints,
and a hand read of the code that handles money or runs unattended. Five real bugs, all fixed and verified.

## 1. Any website you visited could start the scanner on this PC  (`ui/server.py`, `ui/static/app.js`)
`do_POST` guarded `/api/trader/action` and `/api/journal` with an Origin + `X-Quantlab` check, but
**`/api/scan/run` was handled before that check and had none**. A cross-site POST with a simple content type
needs no CORS pre-flight, so any page open in your browser could fire it and spawn `scan.py --top 200` here,
over and over. Fixed: the same guard now covers all three writes, and the page sends the header on the scan call.
Verified against a running copy: no header → 403, `Origin: https://evil.example` → 403, the real page → passes.

## 2. The lab verdict t-statistic exploded on take-profit ideas  (`bear_lab.py`, `scalp_lab.py`)
**The one that could have cost real money.** `t = mean / sd * sqrt(n)` over daily means, guarded only against
`sd == 0`. An idea with a fixed take-profit returns the same percentage on every win, so while a run has no loser
the spread of the daily means is ~0 and t explodes: `cdeep_funding_take` (TARGET = 0.05, every win +4.8% net)
reported **t = 1713** on 7 trades, then **548**. The PASS gate is `day_t >= 2.5`, so it would have been promoted
to 🟡 on arithmetic, not evidence. Three ideas on paper carry TARGET = 0.05.

Fixed: the reported t is now `min(the usual t, the one-sided sign test on daily means as a z)` — the sign test
ignores how big the wins are and asks only how many independent days were positive. **`min_t` is untouched at
2.5**; only the number compared against it was corrected. 5 winning days → 1.86 (was 548, now correctly fails);
12 winning days → 3.49 (a real run still passes); a losing idea keeps its negative t. Six regression tests added.

No idea had reached PASS in either lab, so no past verdict changes. Takes effect at the next daily run.

**The engine hash was re-frozen in the same action.** The lab marks an idea ⛔ TAMPERED if `bear_lab.py` changes,
so editing it alone would have voided 11 days of paper tests on all 26 ideas tomorrow at 09:30. All 26 were
re-registered against the new hash, and the change is recorded in `research/bear_lab/discovery_log.md` and
`BEAR_LAB.md` with the old and new hashes. Idea-file hashes are untouched. Database verified: integrity ok,
26 ideas / 104 screens / 145 evals intact.

## 3. Concurrent requests each ran the same slow scan  (`ui/server.py`)
On a cold or expired cache, `swr()` only consulted `_swr_busy` when a previous answer existed. Every concurrent
request for `/api/support` (≈15 s) therefore started its own scan. Fixed with a per-key lock: one computation per
key, and the second arrival re-checks the cache instead of repeating the work.

## 4. The server grew for as long as it ran  (`ui/server.py`)
`_cache` was never evicted. Each chart you open leaves a klines answer behind permanently. Fixed: a 400-entry
bound that drops the oldest cheap entries and never evicts the expensive `t:` tab answers.

## 5. One bad row would have taken the Forward tab down  (`ui/server.py`)
`paper_books()` did `sum(r["usdt"] for r in closed)` where `usdt` is `None` when `ret_pct` is null, and
`r["exit_time"] // 86400` on a possibly-null column — a single such row turns `/api/forward` into a 502.
There are none today (checked: 0 of 4,500 alerts), so this was latent. Both now skip nulls.
